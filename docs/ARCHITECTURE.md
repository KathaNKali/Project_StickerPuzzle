# Architecture

## Layers
| Layer | Assembly | May use UnityEngine | Owns |
|---|---|---|---|
| Core | `StickerPuzzle.Core` | No (`noEngineReferences`) | Grid, shapes, blocks, doors, movement and exit rules, generator, Checker logic |
| Game | `StickerPuzzle.Game` | Only for ScriptableObjects and file paths | Sessions, level flow, undo, save/restore, data conversion |
| Presentation | `StickerPuzzle.Presentation` | Yes | 3D views, camera, input, animation, UI |
| EditorTools | `StickerPuzzle.EditorTools` | Yes, editor only | Generator scene tools, scene builders, build commands, project setup |
| Tests | `StickerPuzzle.Tests.EditMode`, `.PlayMode` | Yes | Tests |

```
Presentation --> Game --> Core
EditorTools and Tests may reference any of them.
```
Assembly definitions make a wrong-way dependency a compile error. `ArchitectureTests` also checks this at test time.

## Rules
1. Game state lives in Core and Game. Views read state and send commands; they never hold the truth.
2. Core is 2D top-down on a grid. Anything 3D stays in Presentation.
3. Designer data is authored as ScriptableObjects in Game, then converted to plain C# records for Core.
4. Everything saved or shared uses stable string IDs. See [save-system](design/save-system.md).
5. Randomness in Core is seeded and deterministic. Never use `UnityEngine.Random` or the clock in Core.
6. Scenes are generated by scripts in EditorTools so they stay reviewable and reproducible.

## Key patterns
- **Command, then event:** input becomes a command to Game; Core checks the rules; the result is returned as events; views animate those events.
- **Plain state:** Core state is plain data, which keeps save, undo and tests simple.
- **Data-driven content:** shapes and levels are data, referenced by stable ID.

## Data flow
```
Generator scene: settings -> Generator -> board + solution -> Checker -> saved level
Play: Level Data -> Board state
      Input -> Game command -> Core rule check -> new state + events -> save -> views animate
```
